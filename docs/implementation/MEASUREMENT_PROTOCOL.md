# First-wave measurement protocol

## Registration and execution boundary

Protocol ID and candidate revision are in [roadmap.json](roadmap.json). Before measurement, seal the reviewed instance/evaluator/adapter commits, fixture/reference hashes, participant component identities, full dependency locks, source/wheel hashes and actual hardware/image manifest. An observed PyPI version is not an environment lock. The current candidate does not claim those execution gates are complete.

The registered unit is a complete user-facing SDK/component/backend stack on one resource profile. Its implementation may use supported native APIs, plugins or external components declared before the run. The harness may normalize requested inputs and outputs and implement the common training recurrence; it may not substitute missing simulation, differentiation, feed-forward, compilation, conversion or job-recovery functionality for one participant. A hand-coded analytic solution in an adapter is not execution of the requested quantum program. A generally available registered simulator's own optimizations are permitted and attributed.

First-wave exact cases require FP64/complex128 requested computation and the specified outputs; lower precision is not accepted because it is a default or faster. Internal algorithms are disclosed. Compilation and derivative methods may differ within the task contract, with evaluation counts and external components recorded. Dynamics uses the fixed S2 program: algorithmic freedom at matched physical error belongs to a later separate study. First-wave conclusions apply to these contracts and this precision only.

Use the documented recommended stable configuration that meets the contract, with exact options and rationale recorded. An identically named optimization level does not imply equivalent work across SDKs. There is no participant-specific hidden tuning or manual circuit optimization. Offline environment setup has the same budget for all. A future tuned track must freeze equal search/time budgets and count unsuccessful trials separately from the first default-configuration track.

## Resource profile and stopping rules

`CPU1-FP64` is a planned dedicated Ubuntu 24.04 x86_64 host, Python 3.12.14, at least eight physical cores and 64 GiB host RAM. Allocate one pinned physical core and one compute thread to one participant process at a time; do not share its active SMT sibling. Set and record relevant BLAS/OpenMP/backend thread controls, affinity and SDK child-process use. Record the exact CPU, kernel, image digest, BIOS, clock/power policy, SMT, load and dependency versions before comparing any timings. No actual host is selected or benchmarked by this documentation change. If the planned Python/image is unavailable or incompatible, amend the profile openly before any run; do not silently substitute per participant.

The per-case wall and aggregate resident-memory caps are in [FIRST_WAVE.md](FIRST_WAVE.md). The wall cap spans all ten blocks, imports, construction, warmups, measured work, correctness export and cleanup. It is a resource ceiling, not the primary timing statistic. Kill the entire participant process tree at the cap; include child RSS, use OS enforcement and report OOM/timeout explicitly. Compiler cases additionally cap each compilation at 120 seconds. No GPU, multi-node, live QPU or network access during a measured case. No device spending. An offline provider stub supplies events only.

A participant environment gets 1,800 seconds install time and 20 GiB disk. The 24 case caps total **24,060 seconds (6.6833 hours) per registered stack**, including repetition overhead; installation adds at most 0.5 hour per environment. For `S` stack configurations and `E` environments, reserve `6.6833*S + 0.5*E` single-core wall-hours, plus separately budgeted reference/validation work. This is a conservative ceiling even for inapplicable cases, not a promise of useful completion. A two-stack/two-environment pilot ceiling is 14.37 hours plus reference work. Admit campaign size before execution; do not omit slow cases to fit a budget.

Reserve up to one single-core hour and 16 GiB RAM for reference generation, and up to eight single-core hours for evaluator/negative-control qualification; exceeding these planning ceilings requires a disclosed amendment. Reference costs are recorded separately, never charged selectively to a participant. Plan 2 GiB compressed evidence per stack plus 20 GiB per installed environment; a storage overrun is an explicit infrastructure interruption, not permission to discard failures. CPU cloud currency/energy costs cannot be quoted until a host/rate is chosen; record rate, billable resources and actual cost in the run manifest. Hardware/device requests remain zero in P1.

## Blocks, repetitions and randomization

Run ten independent fresh-process blocks per case. For deterministic cases, perform two warmups and three measured repetitions in each block. For sampling, adaptive execution, training and job cases, use zero warmups and one complete measured repetition per block. A compilation is deterministic/seeded: use seeds `[11,23,37,51,73]` twice across the ten blocks, holding the seed fixed within a block. Report seed variability, not only the best route. Training uses its five fixture initializations in that order twice; every initialization must satisfy its progress criterion. Training runs 48 SGD steps each, with held-out checks at steps 0 and 48; additional reference test-loss checkpoints are audit data, not tuning opportunities.

Sampling/adaptive contexts each use 65,536 shots per block. Derive each requested sampling seed by taking the first eight bytes of SHA256 of `sdkbench-first-wave:0.1-candidate-1:<instance>:<block>:<context>` modulo `2**32`; block is 0..9 and context is zero-based fixture order. Shared seed integers do not imply shared random streams. SDKs unable to accept a seed disclose that fact; independence still requires fresh streams and provenance, not replaying a cached sample. No seed hunting or rerunning a failure until it passes.

Counterbalance participant order by rotating the preregistered stack list across blocks; rotate instance order across campaigns. Keep actual timestamps/order and thermal/load observations. Do not run competing participant processes concurrently. An infrastructure interruption is separately evidenced and rerun for all affected measurements; algorithmic failure is retained.

## Timing and metrics

Primary timing uses a monotonic high-resolution clock around the complete requested outcome after module import and input-file loading. Include native object construction, parameter binding, compilation/JIT, required data conversion, execution, backend synchronization/materialization and production of every required output. For W01, construct one reusable native program and evaluate all seven bindings in fixture order in each repetition; no participant-output caching across repeats. Warm repetitions can reuse legitimate runtime/JIT caches but must execute the requested workload. Report cold process/import/setup time separately, and cold versus warm outcome latency without claiming the warm number is end-user startup cost.

Training primary timing spans all 48 update steps and required checkpoints, including quantum/classical transitions; give per-step/evaluation-count diagnostics. Routing reports compilation latency separately from untimed semantic oracle checking; primary routing quality reports legal CZ count and depth with the declared convention. For routing two-body dependency depth, scan the returned ordered program with a layer counter per physical wire initially zero: a CZ is assigned one plus the maximum counter of its two wires and updates both; one-qubit gates do not add two-body layers. Report the largest counter; do not commute/rewrite the returned circuit in this metric. This is an interaction-layer diagnostic, not calibrated physical duration. Interchange primary timing spans parse, export and reimport; independent checking is untimed. Job handling latency is diagnostic only: it is not a client or provider speed leaderboard. Sampling includes production and normalization of all joint counts, not just submission.

Independent oracle computation/evaluator work and harness file I/O are outside primary outcome timers and reported separately; their memory must not contaminate participant RSS. Record host/device memory, construction/binding/compile/execute/normalization sub-times where available, warnings, all declared method options, total SDK evaluations, output hashes and failures. Sub-times are diagnostic and need not sum to primary time when asynchronous work overlaps. Wait explicitly for actual completion before stopping a timer.

Report all per-repetition raw measurements. Within each block, take the median measured time; across ten blocks report median, range and interquartile range. Ten blocks support descriptive comparisons, not a claim that a tiny difference establishes superiority. No automatic significance winner, universal average speedup, or censoring of failed runs. If reporting pairwise descriptive ratios, name the case, matched profile, complete stack and uncertainty limitations; retain both raw values. Broad superiority needs a separately preregistered inferential design.

## Numerical and semantic acceptance

Apply instance thresholds to **every requested scalar, context and required checkpoint**, not merely an average. Use `abs(actual-reference) <= atol + rtol*abs(reference)`; reject nonfinite values, wrong shape/order or missing output. Numerical thresholds are policy choices sized above reference audit residuals, not evidence of application sufficiency everywhere. Review them before release without participant timings. An unacceptable result never contributes an accepted speed value.

For pure-state equivalence, remove at most one physically irrelevant global phase by aligning to the largest-magnitude reference component; then compare amplitudes at the specified absolute tolerance and norm error. This does not permit per-component phases. Reconstruct logical wire order from declared final layouts. The n=6 routing case requires every operator column up to a single operator-wide global phase, plus topology/basis/ancilla legality. For n=8 and n=12, three full-output probe states give bounded evidence only; they are not proof of equivalence for arbitrary inputs. Report this limitation. No known optimal compiler cost is asserted; report quality/compile-time Pareto outcomes rather than a fabricated optimality gap.

Gradient cases compare all three outputs and every Jacobian entry, including near-zero and shared-parameter terms. Training compares each stored parameter and loss checkpoint; gradient values must additionally match the closed-form minibatch chain rule at each step, whether directly exported or independently reevaluated by the validator. Those audit evaluations are separately accounted for, not hidden benchmark-side gradient implementations. Require the specified final loss improvement for each initial seed; no best-seed selection. Dynamics must satisfy both digital-program numeric tolerances and the separate 0.002 absolute physical-observable error ceiling; meeting one does not excuse failure of the other.

QASM2 checks the specified small program's full premeasurement behavior and the classical-bit permutation, not generic whole-language conformance. QASM3 enumerates every reachable branch and reset postcondition. Treat parser acceptance with erased semantics as failure. Job ledgers use exact identity, submission, shot and terminal-status postconditions; a partial/cancelled experiment stays partial. Validate required negative controls before accepting any participant result.

## Distribution equivalence rather than non-rejection

For an alphabet of `K` fixed categories, include zero-count and zero-probability categories and let `N=65536`. Compute empirical total variation `TV_hat = 0.5 * sum_i abs(count_i/N - p_i)`. Use the upper bound

```text
radius = sqrt((K*ln(2) + ln(D/alpha)) / (2*N))
upper_TV = TV_hat + radius + 1e-10
accept only if upper_TV <= 0.04
```

`alpha=0.01`. For W08, `D=20` (two instances times ten blocks); for W02, `D=190` (18 teleportation contexts plus one reset-loop context, times ten blocks). Allocate these budgets per candidate stack/resource profile/workflow, without recycling unused decisions. No confidence claim jointly across all candidates or the whole benchmark is implied. Bounds assume independent shots from a fixed law; a backend using correlated/reused samples must expose that and is outside this sampling profile.

Derivation: total variation between empirical and true categorical laws is the maximum empirical excess probability over all subsets. Apply one-sided Hoeffding to each subset, union-bound over at most `2**K` subsets and `D` decisions, then use the triangle inequality to the specified reference law. The extra `1e-10` reserves reference numerical uncertainty. This is conservative evidence of equivalence within the declared margin, rather than treating failure to reject a wrong distribution as correctness. The acceptance margin is a finite-shot software semantic check, not an experimentally useful error threshold for every application.

Count totals must equal N exactly, with nonnegative integer counts and correct register/branch encoding. Every context and block must pass; record rejected or statistically inconclusive acceptance separately from confirmed deterministic defects. Do not discard branches/postselect. A wrong-angle, swapped-register, omitted-feed-forward and omitted-reset negative control must be rejected at qualification. Exact references and probability normalization are independently audited before participant sampling.

## Status and publication

Keep applicability, implementation readiness and measured outcome as separate fields. Use `not-implemented`, `unsupported`, `install-failed`, `access-blocked`, `not-measured`, `timeout`, `out-of-memory`, `incorrect`, `acceptance-not-established`, and `accepted` with evidence. `not-applicable` requires a preregistered model/role condition from the user contract, never merely absent support. Do not turn failures into zero latency or silently omit them from coverage. Report task-family/variant coverage separately from accepted-case performance.

Publish protocol and review records, environment locks, adapter/component attribution, instance/reference hashes, exported programs, all numeric outputs or joint count histograms, training trajectories, operational event ledgers, raw timing/resource records, failures, costs and limitations. No secrets belong in these artifacts. A public participant may correct a factual adapter/configuration error under the same amendment/rerun rules available to every participant. No private exception to thresholds or retrospective task deletion is allowed.
